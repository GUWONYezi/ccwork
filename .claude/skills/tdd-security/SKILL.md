# tdd-security

Refactor가 끝난 뒤 **커밋 전에** 타입 오류와 보안 취약점을 점검하고, 결과를 심각도별로 분류한다.

점검(1~4단계)은 읽기 전용이다. 고치는 것은 개발자가 승인한 "즉시 수정 필요" 항목뿐이다. 보안 수정은 의존성 버전이나 동작을 바꿀 수 있어서, 도구가 알아서 고치게 하면 리팩토링으로 확보한 안정 상태가 조용히 깨질 수 있기 때문이다.

## 입력

- `$ARGUMENTS`: 이슈 번호 `{N}` (예: `/tdd-security 1`). 보고서 제목과 범위 표시에 쓴다. 다른 기능은 기능 폴더명을 앞에 붙인다 (예: `/tdd-security trash 1`, 생략 시 `tag`).
- 인자가 없으면 시작하지 않고 `docs/features/*/issue-*.md` 목록을 보여주며 어떤 이슈인지 묻고 멈춘다.

## 절대 하지 않는 것

- **테스트 파일(`*.test.ts`, `*.test.tsx`)을 수정하지 않는다.** 타입 오류가 테스트 파일에서 나와도 고치지 않고 보고만 한다 (원인이 구현 쪽 타입이면 구현을 고치는 안을 제시한다).
- **`npm audit fix --force`를 쓰지 않는다.** 메이저 버전 업그레이드를 강제해 호환성을 깨뜨릴 수 있다. `npm audit fix`(비강제)도 승인 없이 실행하지 않는다.
- **판단이 필요한 항목은 승인 없이 수정하지 않는다.** 의존성 업데이트, 동작이 바뀔 수 있는 타입 수정, 비밀값 제거 방식 선택이 여기에 해당한다. 가정으로 진행하지 말고 선택지와 영향을 보여주고 묻는다.
- 4단계 분류와 개발자 승인 전에는 파일을 수정하지 않는다.
- "권장 수정", "무시 가능" 항목은 고치지 않는다. 개발자가 따로 요청하면 그때 한다.
- `.env` 파일의 **값 자체를 출력하지 않는다.** 보고에는 변수 이름과 위치만 적는다 (보고서가 또 다른 유출 경로가 되지 않도록).
- 커밋/푸시는 사용자가 요청할 때만 한다.

## 절차

### 1. 타입 오류 수집

`npx tsc --noEmit`을 실행해 오류 목록(파일, 줄, 코드, 메시지)을 모은다. 오류가 없으면 "0건"으로 기록한다. 테스트 파일에서 난 오류는 표시를 달아 둔다 (수정 금지 대상).

### 2. 의존성 취약점 수집

`npm audit`을 실행해 취약점 목록(패키지, 심각도, 경로, 수정 가능 여부)을 모은다. 네트워크 오류 등으로 실행되지 않으면 추측하지 말고 "점검 불가"로 보고한다. 각 항목이 직접 의존성인지, 개발 전용(devDependency)인지 `npm ls <패키지>`나 `package.json`으로 구분해 둔다. 런타임에 배포되는 코드에 영향이 있는지가 분류의 핵심 근거가 된다.

### 3. .env 변수 노출 확인

Vite는 `VITE_` 접두어가 붙은 변수를 클라이언트 번들에 그대로 포함한다. 그래서 비밀값이 `VITE_*`로 쓰이거나 소스에 직접 박혀 있으면 사용자 브라우저로 노출된다. 아래를 `Grep`으로 확인한다 (테스트 파일 제외 `src/`).

1. `.env*` 파일이 있는지 확인하고(`Glob`), 있으면 **변수 이름만** 읽는다. `.gitignore`에 `.env`가 들어 있는지도 확인한다.
2. `import.meta.env`, `process.env` 사용 지점을 찾는다. `VITE_` 변수 중 이름에 `SECRET`, `KEY`, `TOKEN`, `PASSWORD`, `PRIVATE`이 들어간 것이 있는지 본다.
3. `.env`에 있는 변수 값이 `src/`에 문자열로 하드코딩되어 있는지 (값은 출력하지 않고 일치 여부만 확인).
4. 소스에 박힌 비밀값 패턴: `apiKey`, `secret`, `token`, `password`, `Authorization: Bearer ...`, `sk-`, `AKIA` 등.
5. 이 프로젝트는 `api/notes.ts`에 `API_URL=http://localhost:3001`이 하드코딩되어 있다. 비밀값이 아니라 개발용 주소이므로 "무시 가능(의도된 패턴)"으로 분류하되, 배포 시 환경변수화가 필요하다는 점은 권장으로 언급해도 좋다.

`.env` 파일이 없고 `import.meta.env` 사용도 없으면 "해당 없음"으로 기록한다.

### 4. 분류 및 보고

수집한 결과를 세 가지로 나눠 보고한다. **분류 근거를 항목마다 한 줄로** 적는다. 개발자가 분류가 맞는지 판단할 수 있어야 하기 때문이다.

- **즉시 수정 필요**: 보안 위험 또는 빌드 실패 수준. 예: `tsc`의 컴파일 오류(빌드 `tsc && vite build` 실패), 런타임에 배포되는 의존성의 high/critical 취약점, 클라이언트 번들에 노출되는 비밀값, `.env`가 `.gitignore`에 없음.
- **권장 수정**: 코드 품질 저하. 예: devDependency의 취약점, moderate/low 취약점, `any` 남용, `VITE_` 변수 네이밍 문제, 하드코딩 URL의 환경변수화.
- **무시 가능**: false positive 또는 의도된 패턴. 예: 빌드·배포에 포함되지 않는 개발 도구 경로의 취약점, 로컬 개발 주소, 테스트 파일의 타입 오류(수정 금지이므로 보고만).

형식:

```
보안 점검 결과 (이슈 {N})
수집: tsc {n}건 / npm audit {n}건 / env 노출 {n}건

## 즉시 수정 필요 ({n})
| # | 출처 | 위치 | 내용 | 분류 근거 | 제안 수정 |

## 권장 수정 ({n})
...

## 무시 가능 ({n})
...
```

항목이 없는 분류는 "없음"으로 적는다. **즉시 수정 필요 항목마다 제안하는 수정 방법과 영향 범위**를 함께 보여주고 승인을 기다린다. 분류가 애매하면 더 높은 쪽으로 올리고 이유를 적는다. 모든 분류가 "없음"이면 클린 상태로 보고하고 6단계 없이 끝낸다.

### 5. 승인 후 "즉시 수정 필요"만 처리

개발자가 승인한 항목만 **하나씩** 처리한다.

- **타입 오류**: 구현 파일에서 최소한으로 고친다. 동작이 바뀌면 안 된다. 고친 뒤 `npm test`로 회귀를 확인한다.
- **의존성 취약점**: 승인받은 방법만 쓴다 (예: 특정 패키지 `npm install <pkg>@<버전>`, 또는 비강제 `npm audit fix`). `--force`는 쓰지 않는다. 메이저 업그레이드가 필요하면 영향 범위를 설명하고 별도로 승인받는다. 설치 후 `npm test`와 `npm run build`로 확인한다.
- **노출된 비밀값**: 코드에서 제거하는 방법만 처리한다. 이미 커밋된 비밀이면 키 교체(rotate)가 필요하다는 사실을 알린다. 이력 삭제는 이 스킬이 하지 않는다.
- 항목 하나를 고칠 때마다 관련 검증을 돌리고 실패하면 변경을 되돌린 뒤 개발자에게 보고한다. 고치려다 다른 것을 깨뜨리지 않는 것이 우선이다.

### 6. 재스캔

1~3단계를 다시 실행해 "즉시 수정 필요"가 0건인지 확인한다. 남아 있으면 이유(승인 안 된 항목, 수정 불가, 새로 생긴 항목)와 함께 보고한다. 마지막에 `npm test` 전체 통과도 확인한다.

최종 보고:

- 처리한 항목과 변경 내용 (변경 전/후)
- 재스캔 결과 (tsc / audit / env)와 `npm test` 결과
- 남은 "권장 수정", "무시 가능" 항목 요약
- 테스트 파일을 수정하지 않았고 `--force`를 쓰지 않았다는 확인
- 다음 단계 제안: 커밋 (사용자가 요청할 때)
