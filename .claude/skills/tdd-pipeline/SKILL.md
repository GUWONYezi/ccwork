# tdd-pipeline

이슈 하나를 **Scenarios → Signature → Red → Green → AC 검증 → Refactor → Security** 순서로 진행한다. 각 단계의 실제 작업은 기존 스킬/에이전트가 한다. 이 스킬은 순서를 지키고, **승인과 보고의 관문**을 세우는 역할만 한다.

단계 사이에 사람이 판단해야 하는 지점이 많다(시그니처·시나리오 확정, stub 생성, 실패 테스트 확정, 구현 범위, AC 갭, 리팩토링 대상, 보안 수정). 자동으로 이어가면 이 판단이 조용히 사라지므로, 관문을 건너뛰지 않는 것이 이 스킬의 핵심이다.

## 입력

- `$ARGUMENTS`: 이슈 문서 번호 `{N}` (예: `/tdd-pipeline 1`). 다른 기능은 기능 폴더명을 앞에 붙인다 (예: `/tdd-pipeline trash 1`, 생략 시 `tag`). 이하 `{feature} {N}`은 이 인자를 뜻한다.
- 인자가 없으면 시작하지 않는다. 존재하는 `docs/features/*/issue-*.md` 목록을 보여주고 어떤 이슈인지 묻고 멈춘다.
- `issue-{N}.md`는 없어도 된다. 1단계(`/test-scenarios`)가 이 문서를 만든다. 문서 번호 `{N}`은 GitHub 이슈 제목의 `Tag [N]`이며 일치하는 이슈가 없으면 `/test-scenarios`가 스스로 멈춘다.
- 문서가 이미 있고 `## 시그니처`와 `## 테스트 시나리오`가 둘 다 있으면 1단계를 **개발자에게 물어서** 재사용(스킵)할지 정한다. 스킵은 개발자가 명시적으로 고른 경우에만 한다.

## 절대 하지 않는 것

- **승인 없이 단계를 시작하지 않는다.** 이전 단계의 "다음 진행해도 되나요?"에 대한 명시적 긍정 답변이 있어야 한다. 침묵, 이전 단계 승인, "알아서 해"로 읽히는 모호한 답은 승인이 아니다. 모호하면 다시 묻는다.
- **단계를 건너뛰거나 순서를 바꾸지 않는다.** 건너뛰고 싶다는 요청은 개발자가 직접 말했을 때만 따르고, 건너뛴 사실을 보고에 남긴다.
- 보고 없이 다음으로 넘어가지 않는다. 단계가 **완료**됐든 **중간에 멈췄든**(실패, 5회 초과, 하위 스킬이 승인/질문을 요청) 모두 보고한다.
- 하위 스킬의 "절대 하지 않는 것"을 이 스킬이 우회하지 않는다. 테스트 파일 수정, 시나리오 변경, `npm audit fix --force`, 범위 밖 수정 등은 단계 스킬의 규칙이 그대로 적용된다.
- ac-verifier의 갭을 이 스킬이 직접 고치지 않는다. 판단은 개발자 몫이다.
- 커밋/푸시는 하지 않는다. 개발자가 요청할 때만 한다.

## 관문 규칙 (모든 단계 공통)

각 단계는 아래 네 박자로 진행한다.

1. **시작 전 승인 요청**: 이번 단계가 무엇을 하고 어떤 파일을 건드리는지 2~3줄로 알리고 승인을 받는다.
2. **실행**: 승인받은 단계만 실행한다. 하위 스킬이 중간에 개발자 승인을 요구하면(refactor 대상 목록, security 수정 등) 그 질문을 그대로 개발자에게 전달하고 답을 기다린다. 이 스킬의 시작 승인이 하위 스킬 내부 승인을 대신하지 않는다.
3. **보고**: 완료 또는 중단 시점에 아래 형식으로 보고한다.
4. **다음 단계 승인 요청**: 보고 끝에 다음 단계를 안내하고 진행 여부를 묻는다. 답이 올 때까지 멈춘다.

### 보고 형식

```
## [{단계 번호}/7] {단계명} — {완료 | 중단 | 실패}

- 한 일: (파일 목록, 건수)
- 결과: (테스트 통과/실패 수, 판정 등 핵심 수치)
- 특이사항: (경고, 스킵, 기존에 실패하던 테스트, 하위 스킬이 남긴 제안)
- 건드리지 않은 것 확인: (테스트 파일 / db.json 등 해당 단계에서 지켜야 할 것)

다음: {다음 단계명} — 진행할까요? (진행 / 수정 요청 / 중단)
```

### 중단 시 선택지

단계가 완료되지 못했으면(하위 스킬이 멈춤, 5회 실패, 전제 조건 불충족) 보고에 원인과 함께 선택지를 준다. 추천이 있으면 첫 번째로 적는다.

- 같은 단계 재시도 (필요한 선행 조치가 있으면 함께 안내)
- 이전 단계로 돌아가기 (예: Green이 collect 실패로 멈추면 Signature, 시나리오가 틀렸으면 1단계 `/test-scenarios`)
- 파이프라인 중단

개발자가 고르기 전에는 아무것도 실행하지 않는다.

## 절차

### 0. 사전 확인

1. `docs/features/{feature}/issue-{N}.md`가 있는지, 있으면 두 섹션(`## 시그니처`, `## 테스트 시나리오`)이 있는지와 시나리오 체크박스 총 건수를 확인한다. 문서가 없으면 "1단계에서 새로 만든다"로 기록한다.
2. `git status --short`로 시작 시점의 작업 트리를 기록한다. 이미 수정되어 있던 파일(`db.json`, `package.json` 등)은 이후 "이 파이프라인이 바꾼 것"과 구분하기 위한 기준이다.
3. 개발자에게 **전체 계획과 시작 상태**를 보여준다.

```
이슈 {feature} {N}: {제목 또는 "문서 없음, 1단계에서 생성"}
시나리오 {M}건 또는 "없음" / 시작 시점 작업 트리: {변경 파일 목록}

진행 순서 (단계마다 시작 전 승인 + 종료 후 보고):
 1. /test-scenarios  시그니처 확정 + 테스트 시나리오 도출
 2. /tdd-signature  빈 시그니처 생성
 3. /tdd-red        실패하는 테스트 작성
 4. /tdd-green      최소 구현
 5. ac-verifier     AC 충족 독립 검증
 6. /tdd-refactor   구조 개선
 7. /tdd-security   타입/취약점/비밀값 점검
```

4. 1단계 시작 승인을 받는다. 답이 오기 전에 아무것도 실행하지 않는다.

### 1. /test-scenarios

- 문서가 이미 있고 두 섹션이 모두 있으면, 재사용(스킵)할지 새로 도출할지 먼저 묻는다. 스킵하면 보고에 "1단계 스킵(기존 문서 재사용)"으로 남기고 시나리오 건수만 확인한다. 덮어쓰기가 필요하면 `test-scenarios`가 문서 덮어쓰기 여부를 직접 묻는다.
- 승인 후 `Skill`로 `test-scenarios`를 `{N}` 인자와 함께 실행한다. 이 스킬은 내부에서 **시그니처 승인**과 **시나리오 승인**을 각각 따로 받고, 승인 전에는 파일에 쓰지 않는다. 시작 승인과 별개이므로 시그니처, 시나리오, AC 커버리지를 개발자에게 그대로 전달하고 답을 기다린다.
- 이 단계는 `issue-{N}.md`만 쓴다. 구현 코드와 테스트 코드는 쓰지 않는다.
- 보고: `issue-{N}.md` 경로, 확정된 시그니처 대상 파일 목록, 시나리오 건수(정상/경계/예외), AC 커버리지에서 비어 있는 AC가 없다는 확인, 기록 전 승인 두 번이 모두 있었다는 확인.
- 이슈를 못 찾거나(`Tag [N]` 없음/중복) 개발자가 시그니처·시나리오를 승인하지 않아 끝나지 않으면 중단으로 보고한다. 문서가 완성되지 않았으므로 2단계로 넘어가지 않는다.

### 2. /tdd-signature

- 승인 후 `Skill`로 `tdd-signature`를 `{feature} {N}` 인자와 함께 실행한다 (feature가 `tag`면 `{N}`만).
- 보고: 새로 만든 stub 파일, 이미 있어 스킵한 파일, 테스트 파일을 건드리지 않았다는 확인.
- stub이 `not implemented`를 던지는 상태이므로 이후 단계에서 테스트가 실패하는 것이 정상임을 한 줄로 알린다.

### 3. /tdd-red

- 승인 후 `Skill`로 `tdd-red`를 실행한다.
- 보고: 작성한 테스트 파일, 테스트 건수와 시나리오 건수 일치 여부, `npm test` 결과(**전부 실패해야 정상**), src 구현 코드를 건드리지 않았다는 확인.
- 일부가 통과하거나 건수가 안 맞으면 정상이 아니므로 중단으로 보고하고 선택지를 준다.

### 4. /tdd-green

- 승인 후 `Skill`로 `tdd-green`을 실행한다.
- 보고: 구현한 파일, 이슈 테스트 통과/전체, 전체 `npm test`와 회귀 여부, 체크한 시나리오 `[x]` 수/전체, 커버리지와 미커버 라인, 테스트 파일·`db.json` 미변경 확인.
- collect 실패 감지, 5회 실패 같은 중단은 사유와 함께 보고하고 중단 선택지를 준다. 이 경우 5단계로 넘어가지 않는다.

### 5. ac-verifier 검증

- 승인 후 `Agent` 도구로 `ac-verifier` 에이전트를 실행한다. 프롬프트에는 `{feature} {N}`과 "파일을 수정하지 말고 AC별 판정만 보고"를 담는다. 에이전트는 이 대화의 맥락을 모르므로 필요한 정보(기능 폴더, 이슈 번호, 시나리오 문서 경로)를 프롬프트에 직접 넣는다.
- 보고: AC별 ✅/⚠️/❌ 판정, 요약 건수, 수동 확인 필요 항목, 에이전트가 제안한 추가 시나리오를 **원문 그대로** 전달한다. 요약하다가 근거(`파일:줄`)가 빠지지 않게 한다.
- ⚠️/❌가 있으면 이 스킬이 임의로 고치지 않는다. 선택지를 제시한다.
  - 갭을 감수하고 Refactor로 진행 (⚠️/❌를 보고에 남김)
  - `/test-scenarios`(1단계)로 시나리오 보강 후 Red부터 다시 (추천: 테스트가 없는 ❌일 때)
  - `/tdd-green`으로 구현 보완 (구현 누락 ❌일 때)
  - 파이프라인 중단
- 모두 ✅여도 "수동 확인 필요" 항목은 따로 알린다.

### 6. /tdd-refactor

- 승인 후 `Skill`로 `tdd-refactor`를 실행한다. 이 스킬은 내부에서 **대상 목록 승인**을 따로 받는다. 시작 승인과 별개이므로 목록을 개발자에게 그대로 전달하고 답을 기다린다.
- 보고: 승인된 항목과 적용 결과, 롤백된 변경, 매 변경 후 `npm test` 결과, 테스트 파일 미변경 확인. 후보가 없어 끝났으면 그 사실을 보고한다.

### 7. /tdd-security

- 승인 후 `Skill`로 `tdd-security`를 실행한다. 이 스킬도 내부에서 "즉시 수정 필요" 항목의 **수정 승인**을 따로 받는다. 그대로 전달한다.
- 보고: 즉시 수정 필요 / 권장 수정 / 무시 가능 분류 결과, 처리한 항목, 재스캔 후 클린 여부, 마지막 `npm test` 결과.

### 8. 최종 보고

일곱 단계가 끝나면(또는 개발자가 중단하면) 전체를 한 번에 정리한다.

- 단계별 상태 표 (완료 / 스킵 / 중단)
- 파이프라인이 바꾼 파일 목록 (0단계 기준 대비). 시작 전부터 수정되어 있던 파일은 구분
- 최종 `npm test` 결과, 시나리오 체크 `[x]` 수/전체, AC 판정 요약
- 남은 이슈: ⚠️/❌로 넘어간 AC, 권장 수정 보안 항목, 수동 확인 필요 항목
- 다음 제안: 커밋은 개발자가 요청할 때 한다. 커밋 규칙(`type: 제목` 50자 이하)과 `db.json` 같은 의도치 않은 변경 제외를 상기시킨다. 커밋/푸시는 하지 않는다.
