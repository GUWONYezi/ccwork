# e2e-write

PRD의 **사용자 스토리**를 Playwright E2E 테스트로 바꾼다.

E2E는 느리고 깨지기 쉬운 대신, 단위 테스트가 줄 수 없는 것을 준다. UI → Context → API → `db.json`이 실제로 이어지는지, 그리고 사용자가 그 흐름을 끝까지 완주할 수 있는지다. 그래서 이 스킬의 모든 판단 기준은 하나다. **"이 검증은 E2E에서만 잡을 수 있는가?"** 단위 테스트가 이미 잡는 것을 브라우저로 다시 돌리면 비용만 늘고 실패 원인은 흐려진다.

## 입력

- `$ARGUMENTS`: 기능 폴더명 (예: `/e2e-write tag` → `docs/features/tag/prd.md`). 생략하면 `docs/features/` 아래 `prd.md`가 있는 기능 목록을 보여주고 묻는다.
- `prd.md`가 없거나 사용자 스토리 섹션이 없으면 시작하지 않고 알린다. 스토리 섹션 번호는 PRD마다 다르다(tag는 `## 3.`, trash/search는 `## 2.`). 번호가 아니라 제목 "사용자 스토리"로 찾는다.

## 절대 하지 않는 것

- **승인 없이 코드를 쓰지 않는다.** 시나리오 표(2단계)를 먼저 보여주고 승인받는다. CLAUDE.md의 TDD 사이클처럼 각 단계에 사람의 게이트가 있기 때문이다.
- `src/`를 수정하지 않는다. 요소를 잡을 접근 가능한 이름이 없으면 `data-testid`를 몰래 심지 말고 어떤 요소가 문제인지 보고한다. 접근성 개선은 별도 결정이다.
- 개발용 `db.json`(`localhost:3001` 개발 서버)을 건드리지 않는다. E2E는 `playwright.config.ts`가 띄우는 별도 API(`e2e/seed.json` 복사본)만 쓴다.
- 실행 중인 개발 서버 프로세스를 임의로 종료하지 않는다. 3001 포트 충돌이 나면 사용자에게 서버를 끄도록 안내한다.
- PRD의 **Out of Scope** 항목을 시나리오로 만들지 않는다. 일부러 만들지 않기로 한 동작이다. (예: tag는 "NoteItem에 태그 이름 직접 표시", "이탈 확인창"이 범위 밖이다.)
- 커밋/푸시는 사용자가 요청할 때만 한다.

## 절차

### 1. 읽기

1. `docs/features/{feature}/prd.md`: 사용자 스토리, Out of Scope, 용어 정의(화면에 보이는 문구와 동작 이름을 맞출 때 쓴다).
2. **이미 단위 테스트가 검증하는 것 파악**: `src/**/*.test.{ts,tsx}`와 `docs/features/{feature}/issue-*.md`의 시나리오를 훑어 어떤 규칙이 하위 레벨에서 보장되는지 정리한다. 이 목록이 중복을 거르는 기준이다.
3. **구현 현황 확인**: 스토리가 가리키는 컴포넌트/기능이 `src/`에 실제로 있는지 본다. 아직 없으면 E2E가 전부 실패할 것이므로 사용자에게 알리고 계속할지 묻는다. E2E는 보통 기능이 Green이 된 뒤에 쓴다.
4. **요소를 잡을 근거 확인**: 관련 컴포넌트(`NoteEditor`, `NoteItem`, `Layout`, `TagInput` 등)를 읽어 버튼 문구, `aria-label`, `role`을 확인한다. 로케이터는 코드에서 확인한 이름으로만 쓴다. 추측한 문구로 쓰면 첫 실행에서 깨진다.
5. `playwright.config.ts`, `e2e/` 기존 파일(`seed.json`, `helpers/`, 기존 spec)을 읽어 재사용할 것을 파악한다.

### 2. 스토리 → 시나리오 변환 (승인 게이트)

스토리를 하나씩 분류해서 **표로** 보여준다. 모든 스토리가 표에 나와야 한다. 빠진 스토리가 없어야 사용자가 판단할 수 있기 때문이다.

| 스토리 | 처리 | E2E 시나리오(제목) 또는 제외 사유 |
| ------ | ---- | --------------------------------- |

처리 값은 셋 중 하나다.

- **E2E**: 브라우저 + API를 관통해야만 검증되는 여정. 시나리오 제목은 `사용자가 ~하면 ~된다` 형태의 한국어 한 문장.
- **병합**: 같은 화면 흐름의 스토리 여러 개를 한 시나리오로 묶는다. 예: "추가한다 → 저장한다 → 새로고침 후에도 보인다"는 한 여정이다. 스토리마다 테스트 하나씩 만들면 같은 준비 동작이 반복돼 느려지고, 실제 사용 흐름과도 멀어진다.
- **제외**: 아래 중 하나에 해당하면 제외하고 사유를 쓴다.
  - 단위/컴포넌트 테스트가 이미 검증 (어느 테스트 파일인지 명시)
  - PRD Out of Scope
  - 순수 시각 표현(색, 간격, hover 스타일)처럼 기능 검증이 아닌 것

표 아래에 시나리오별 한 줄 요약(준비 데이터 → 사용자 동작 → 최종 확인)을 붙이고 승인을 기다린다. 사용자가 고르거나 뺄 수 있게 열어 둔다.

### 3. 코드 작성

승인된 시나리오만 `e2e/{feature}.spec.ts`에 쓴다. 기존 파일이 있으면 덮어쓰지 말고 읽은 뒤 시나리오를 추가한다. 템플릿과 헬퍼 예시는 `references/spec-template.md`를 따른다.

**원칙 (이유와 함께)**

- **사용자 관점으로 쓴다.** 로케이터는 `getByRole`, `getByLabel`, `getByText` 순으로 고른다. 사용자가 화면에서 인지하는 방식이고, 마크업이나 클래스가 바뀌어도 안 깨지기 때문이다. CSS 클래스·DOM 구조 의존 셀렉터는 쓰지 않는다. 이 프로젝트는 입력창에 `aria-label`을 붙이는 규칙(디자인 시스템 Do)이 있어 대부분 `getByLabel`로 잡힌다.
- **테스트는 서로 독립이다.** 다른 테스트가 남긴 데이터나 실행 순서에 기대지 않는다. 각 테스트가 시작할 때 API(`request` fixture)로 자기 노트를 직접 만들고, 끝나면 지운다. UI로 준비 단계를 반복하면 느리고, 준비 단계가 깨지면 무관한 테스트까지 실패한다. UI 조작은 **검증하려는 여정**에만 쓴다. 제목에 테스트별 고유값을 넣어 다른 노트와 헷갈리지 않게 한다.
- **시드 데이터 순서에 의존하지 않는다.** 목록의 n번째 노트를 고르지 말고 고유 제목으로 찾는다.
- **고정 대기 금지.** `waitForTimeout`, `sleep`을 쓰지 않는다. `expect(locator).toBeVisible()` 같은 자동 재시도 단언을 쓰면 느린 환경에서도 안정적이다. 저장 같은 비동기 동작은 화면에 나타나는 결과를 기다리거나, 필요하면 `page.waitForResponse`로 요청 완료를 기다린다.
- **영속성은 새로고침으로 증명한다.** "저장했다"는 스토리는 화면 갱신만으로는 부족하다. `page.reload()` 뒤에도 남는지 확인해야 서버 반영이 검증된다. 이것이 단위 테스트(API mock)가 못 하는 E2E 고유 가치다.
- **테스트 하나는 여정 하나, 단언은 여정의 결과를 확인하는 것만.** 중간 단계마다 단언을 쌓지 않는다. 다만 여정이 중간 상태 확인 없이는 의미가 없으면(예: 입력창이 열려야 입력 가능) 필요한 만큼만 둔다.
- **중복 금지의 구체적 기준.** 입력 규칙의 경계값 조합(길이 49/50/51, 대소문자·공백 변형, 개수 제한 경계)은 `utils` 단위 테스트의 몫이다. E2E에서는 "중복 입력 시 안내가 나온다" 같은 **사용자가 규칙을 만나는 대표 경로 하나**만 둔다. 컴포넌트 props별 렌더링, 훅 상태 전이, 에러 객체 형태도 마찬가지로 E2E에서 확인하지 않는다.
- **에러/실패 경로는 신중히.** 서버 장애 같은 경로는 `page.route`로 API를 실패시켜야 하는데, PRD가 요구한 스토리일 때만 쓴다. 이 프로젝트는 실패 시 `alert`를 띄우므로 `page.on('dialog')`로 받는다.
- 구조는 `test.describe('{기능명}')` 아래 `test('사용자가 ~하면 ~된다')`. 각 테스트 위에 주석으로 대응 스토리를 한 줄 남겨 PRD와 추적할 수 있게 한다. UI 문구는 한국어 그대로 쓴다.
- Prettier(작은따옴표, 세미콜론, 2칸, printWidth 100)와 TypeScript strict를 따른다.

### 4. 실행과 검증

1. `npx playwright test e2e/{feature}.spec.ts`로 실행한다. 3001 포트 충돌 에러가 나면 개발 서버를 끄도록 안내하고 멈춘다(프로세스를 대신 종료하지 않는다).
2. 실패하면 원인을 세 갈래로 나눠 판단한다. 테스트 코드의 문제(로케이터/대기)면 고친다. 앱의 실제 버그면 고치지 말고 **버그로 보고**한다(E2E가 존재하는 이유다). 접근성/로케이터 근거 부족이면 `src` 수정 제안으로 보고한다. 테스트를 통과시키려고 단언을 약화하지 않는다.
3. 한 번 통과했다고 끝내지 않는다. 불안정(flaky) 여부를 보려고 `--repeat-each=3`으로 한 번 더 돌린다. 간헐 실패는 대기/독립성 문제의 신호다.
4. `npm test`(vitest)가 여전히 통과하는지 확인한다. `vite.config.ts`의 `exclude: ['e2e/**']`가 e2e 파일을 vitest에서 빼 준다. 빠져 있지 않으면 알린다.

### 5. 보고

다음을 간결하게 보고하고 멈춘다. 다음 단계는 사용자가 정한다.

- 작성한 시나리오 수와 파일 경로, 제외한 스토리와 사유 요약
- 실행 결과(통과/실패, `--repeat-each` 결과)
- 발견한 앱 버그나 `src` 개선 제안(있을 때만)
- 커밋하지 않았다는 사실 (커밋 시 `test: 제목` 형식, 제목 50자 이하 규칙 적용)
