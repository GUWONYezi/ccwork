# tdd-refactor

`tdd-green`으로 테스트가 통과한 뒤, **동작은 그대로 두고 구조만 개선**한다. TDD의 Refactor 단계다.

리팩토링은 테스트가 안전망일 때만 의미가 있다. 그래서 (1) 시작 전에 전부 통과인지 확인하고, (2) 변경을 하나씩 쪼개 매번 테스트를 돌리며, (3) 깨지면 고치려 들지 않고 되돌린다. 한 번에 많이 바꾸면 어떤 변경이 테스트를 깨뜨렸는지 알 수 없고, 깨진 상태에서 디버깅하면 리팩토링이 아니라 새 개발이 된다.

## 입력

- `$ARGUMENTS`: 이슈 번호 `{N}` (예: `/tdd-refactor 1`). 이슈 번호는 보고와 시나리오 문서(`docs/features/tag/issue-{N}.md`) 참조에 쓴다. 다른 기능은 기능 폴더명을 앞에 붙인다 (예: `/tdd-refactor trash 1`, 생략 시 `tag`).
- 인자가 없으면 시작하지 않고 `docs/features/*/issue-*.md` 목록을 보여주며 어떤 이슈인지 묻고 멈춘다.

## 절대 하지 않는 것

- **새 기능을 추가하지 않는다.** 외부에서 관찰되는 동작(렌더 결과, 함수의 입출력, API 호출)은 그대로여야 한다. 동작이 바뀌는 변경은 리팩토링이 아니다.
- **테스트 파일(`*.test.ts`, `*.test.tsx`)을 수정하지 않는다.** 테스트는 "동작이 안 바뀌었다"는 증거다. 증거를 고치면 의미가 없다. 테스트가 깨지면 코드 쪽을 되돌린다.
- **`src/` 밖의 파일을 수정하지 않는다.** 문서, 설정, `db.json`, `package.json` 포함. 시나리오 문서 체크박스도 건드리지 않는다.
- **3단계에서 추출한 대상 파일 범위 밖을 수정하지 않는다.** 이번 이슈와 무관한 파일을 건드리면 diff가 커지고 리뷰가 어려워진다. 대상 밖 파일에서 문제를 발견하면 수정하지 말고 보고서에 "범위 밖 발견"으로만 적는다.
- 테스트 통과가 확인되지 않은 상태로 다음 변경으로 넘어가지 않는다.
- 커밋/푸시는 사용자가 요청할 때만 한다.

## 절차

### 1. CLAUDE.md 읽기

`CLAUDE.md`를 읽고 프로젝트 컨벤션(컴포넌트 패턴, 분리 원칙, 네이밍, 스타일링, 상태관리/API 패턴)을 파악한다. 이 프로젝트에서 "좋은 구조"의 기준은 범용 취향이 아니라 이 문서다. 디자인 시스템 관련 클래스를 바꿀 가능성이 있으면 `docs/design-system/rules/do-and-dont.md`도 본다. 리팩토링이 스타일 외형을 바꾸면 안 되므로, 스타일은 기본적으로 건드리지 않는다.

### 2. 기준선 확인

`npm test`를 실행한다. **전체 통과여야만** 시작한다. 이미 실패하는 테스트가 있으면 리팩토링 중 깨진 것인지 원래 깨진 것인지 구별할 수 없기 때문이다. 실패가 있으면 목록을 보여주고 `/tdd-green {N}`을 먼저 하도록 안내하고 멈춘다. `db.json`은 이미 수정된 상태일 수 있으니 그대로 둔다.

### 3. 리팩토링 대상 파일 식별

1. `git diff main...HEAD --name-only -- src/`로 이번 브랜치에서 변경된 `src/` 파일 목록을 얻는다.
2. `*.test.ts`, `*.test.tsx`는 제외한다.
3. 남은 파일이 **수정 허용 범위**다. 목록이 비어 있으면 "리팩토링할 대상 파일이 없다"고 보고하고 멈춘다.
4. `main...HEAD`는 커밋된 변경만 포함한다. 아직 커밋하지 않은 `src/` 변경이 있으면(`git status`로 확인) 그 파일도 이번 이슈 변경으로 보고 목록에 합치되, 보고에서 "미커밋 변경 포함"이라고 밝힌다. 이슈와 무관해 보이는 파일이 섞였으면 개발자에게 확인한다.

### 4. 점검

대상 파일을 읽고 아래 기준으로 검토한다. 기준에 걸리는 것만 후보로 올린다. 문제없는 코드를 억지로 바꾸지 않는다.

- **중복 제거**: 같은 로직이 반복되는가
- **네이밍 명확성**: 의도를 드러내는 이름인가
- **단일 책임**: 하나의 함수/컴포넌트가 너무 많은 일을 하는가 (CLAUDE.md 분리 원칙: 규칙은 `utils`, 상태·동작이 둘 이상이면 `hooks`, 표현은 순수 컴포넌트. 단 "둘 이상일 때만" 분리한다)
- **불필요한 복잡도**: 매직 넘버, 과도한 중첩, 불필요한 추상화
- **CLAUDE.md 컨벤션 불일치**: named export, 파일명=export명, `XxxProps` 위치, early return, `onXxx`/`handleXxx`, `isXxx`, 한국어 주석·문구 등

각 후보에 대해 "동작이 안 바뀌는가"를 먼저 따진다. 확신이 없으면 후보에서 뺀다.

### 5. 대상 목록 보고 → 승인 대기

수정은 아직 시작하지 않는다. 아래 형식으로 보고하고 **개발자의 승인을 기다린다**.

```
리팩토링 대상 (이슈 {N}) — 기준선: npm test 전체 통과 (N개)

대상 파일 범위: <파일 목록>

| # | 파일 | 기준 | 내용 | 위험도 |
|---|------|------|------|--------|
| 1 | src/utils/tags.ts | 매직 넘버 | 20, 10을 상수로 | 낮음 |

범위 밖 발견 (수정하지 않음): <있으면>
```

개발자가 일부만 승인하거나 항목을 바꿔 달라고 하면 그대로 따른다. 승인 없이 진행하지 않는다. 후보가 하나도 없으면 "개선할 점이 없다"고 보고하고 끝낸다.

### 6. 하나씩 변경 → 테스트

승인된 항목을 **하나씩** 처리한다.

1. 변경 하나를 적용한다 (범위 밖 파일, 테스트 파일은 절대 건드리지 않는다).
2. `npm test`를 실행한다.
3. 전체 통과면 다음 항목으로 넘어간다. 이때 린트/타입 오류를 만들지 않았는지 `npx tsc --noEmit`로도 확인하면 좋다 (`npm run lint`는 `--fix`로 파일을 바꾸므로 쓰지 않는다).
4. 어느 항목이든 한 번에 여러 파일을 바꿔야 하면 "하나의 변경"은 그 논리적 단위 하나다. 단, 한 변경에 서로 다른 목적을 섞지 않는다.

### 7. 깨지면 즉시 롤백

테스트가 실패하면 **그 즉시** 방금 변경을 되돌린다. 고치려고 이어서 수정하지 않는다. 되돌릴 때는 방금 수정한 파일을 직접 이전 내용으로 복원한다 (`git checkout`/`git stash`는 다른 미커밋 변경까지 날릴 수 있으니 쓰지 않는다. 변경 전 내용은 적용 직전에 기억해 두거나 Edit의 역방향으로 복원한다). 복원 후 `npm test`로 다시 전체 통과를 확인한다.

그다음 **다른 접근**을 시도한다 (예: 더 작게 쪼개기, 다른 방식). 같은 항목에서 두 번 다른 접근을 해도 깨지면 그 항목은 포기하고 보고서에 "건너뜀: 사유"로 적는다. 테스트가 깨지는 건 동작이 바뀌었다는 신호이므로 무리하게 밀어붙이지 않는다.

### 8. 변경 요약

아래를 보고한다.

- **적용한 항목**별 변경 전/후 요약 (핵심 코드 조각 포함). 가능하면 `git diff -- src/`의 요점
- **건너뛴 항목**과 사유 (롤백한 것 포함)
- **최종 `npm test` 결과** (전체 통과 수)
- **확인 사항**: 테스트 파일·`src/` 밖·대상 범위 밖 파일을 수정하지 않았다는 것, 새 기능을 추가하지 않았다는 것
- **범위 밖 발견**: 수정하지 않고 적어 두는 것들
