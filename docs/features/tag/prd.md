# 태그 기능 PRD (뼈대)

> 기준 문서: [`spec-fixed.md`](./spec-fixed.md) (확정본). 이 문서는 기능 정의서를 바탕으로 한 PRD 뼈대이며, 4번(기술 결정)은 다음 세션에서 논의해 채운다.

## 1. 컴포넌트 개요 (요약과 배경)

### 요약

노트에 문자열 태그를 추가·삭제하고, 노트 상세 화면(NoteEditor)에서 태그 목록을 확인하며, 왼쪽 노트 목록(NoteItem)에서 태그가 있는 노트를 한눈에 구분할 수 있게 하는 기능이다. 태그는 `Note.tags?: string[]`로 노트 객체 안에 저장하고, 표현은 순수 컴포넌트 `Tag`가 담당한다.

### 배경 및 근거

- 현재 노트는 제목/내용만 가지고 있어, 노트가 늘어나면 성격이 비슷한 노트를 묶거나 구분할 방법이 없다.
- `src/types/note.ts`에 "tags 필드는 아직 없음"이라는 주석이 남아 있을 만큼, 태그는 이 프로젝트에서 처음부터 계획된 확장 지점이다.
- 태그는 기존 CRUD 흐름(타입 → API → Context → 컴포넌트)을 그대로 확장하는 비교적 작은 변경이라, 계층 구조와 TDD를 연습하기에 적합한 범위이다.

### 기획 및 개발의 중요성

- **기획**: 입력 규칙(trim, 대소문자 무시 중복, 50자/10개 제한)과 저장 시점(저장 버튼 시 일괄 반영)을 먼저 확정하지 않으면 UI와 테스트 기준이 흔들린다. 그래서 정의서에서 11개 질의응답으로 규칙을 확정했다.
- **개발**: 옵셔널 필드(`tags?`)라 기존 `db.json` 노트에서 깨지지 않아야 하고(`note.tags ?? []`), 노트 전환 시 로컬 state 리셋을 놓치면 이전 노트의 태그가 섞여 저장될 수 있다. 데이터 호환성과 상태 동기화가 핵심 위험이다.
- 디자인 시스템 마이그레이션이 진행 중이므로, 신규 `Tag` 컴포넌트는 `docs/design-system/` 기준을 따른다.

## 2. 핵심 사용자 정의

### 사용자 분석

이 앱은 로컬에서 동작하는 단일 사용자용 노트 앱이다(인증/공유 없음). 주된 사용자는 다음과 같다.

| 사용자                    | 특징                                                                  | 주요 목표                              |
| ------------------------- | --------------------------------------------------------------------- | -------------------------------------- |
| 개인 노트 작성자          | 학습·업무 메모를 자주 작성하고, 시간이 지나 노트가 수십 개로 늘어난다 | 쌓인 노트를 주제별로 구분해 관리       |
| 빠른 메모를 남기는 사용자 | 짧은 메모를 연속해서 작성하며, 키보드 위주로 입력한다                 | 입력 흐름을 끊지 않고 분류 정보를 추가 |
| 기존 노트 사용자          | 태그 도입 이전에 작성한 노트(`tags` 없음)를 계속 사용한다             | 기존 노트가 그대로 열리고 편집됨       |

### 태그가 없을 때 겪는 불편

- 노트가 늘어날수록 제목과 내용을 일일이 열어봐야 노트의 성격을 알 수 있다.
- 비슷한 주제의 노트를 묶어 인식할 방법이 없어, 제목에 `[업무]` 같은 접두어를 직접 붙이는 식의 임시 방편이 필요하다.
- 왼쪽 목록에서 분류된 노트와 아닌 노트를 구분할 시각 단서가 없다.
- 분류 정보를 제목이나 본문에 섞어 쓰게 되어 제목과 본문이 지저분해진다.

## 3. 사용자 스토리

2번에서 정의한 사용자를 기준으로 작성한다.

### 개인 노트 작성자

- 노트 작성자로서, 노트에 태그를 추가하고 싶다. 그래야 노트의 주제를 표시할 수 있다.
- 노트 작성자로서, 잘못 붙인 태그를 삭제하고 싶다. 그래야 분류를 바로잡을 수 있다.
- 노트 작성자로서, 노트 상세 화면에서 붙은 태그 목록을 보고 싶다. 그래야 노트를 열자마자 분류를 파악할 수 있다.
- 노트 작성자로서, 왼쪽 목록에서 태그가 있는 노트를 구분하고 싶다. 그래야 노트를 열지 않고도 분류된 노트를 알 수 있다.

### 빠른 메모를 남기는 사용자

- 빠른 메모 사용자로서, 태그 입력창에서 Enter만으로 태그를 연속해서 추가하고 싶다. 그래야 마우스 없이 빠르게 분류할 수 있다.
- 빠른 메모 사용자로서, 같은 태그를 실수로 다시 입력했을 때 안내를 받고 싶다. 그래야 중복 없이 정리된 태그를 유지할 수 있다.
- 빠른 메모 사용자로서, 태그 입력창을 필요할 때만 열고 닫고 싶다. 그래야 평소에는 화면이 복잡해지지 않는다.

### 기존 노트 사용자

- 기존 노트 사용자로서, 태그가 없는 예전 노트도 에러 없이 열고 저장하고 싶다. 그래야 기존 데이터가 그대로 유지된다.
- 기존 노트 사용자로서, 태그를 추가·삭제한 뒤 "저장"을 눌렀을 때만 서버에 반영되길 원한다. 그래야 제목·내용과 같은 방식으로 일관되게 편집할 수 있다.

## 4. 기술 결정 (ADR)

### ADR-001: 태그 기능 아키텍처 — 노트 내부 배열 + 로직 분리 (B안)

- **Status**: 확정

- **Context**:
  - 정의서(`spec-fixed.md`)가 `Note.tags?: string[]`, `db.json` 무수정, 저장 버튼 시 일괄 반영을 확정했다.
  - 입력 규칙이 많다(trim, 빈 값 무시, 대소문자 무시 중복, 50자, 10개, 안내 문구). 입력창 열기/닫기, 노트 전환 시 리셋까지 더하면 상태도 많다.
  - 현재 `NoteEditor`는 폼 동기화 `useEffect`와 저장 로직을 이미 갖고 있고, 프로젝트에는 테스트 파일이 하나도 없다. TDD로 진행하므로 규칙을 렌더링 없이 검증할 수 있어야 한다.
  - 코드 확인 결과 `api.updateNote`는 `Partial<Note>`, `api.createNote`는 `Omit<Note, ...>`를 받아 `Note` 타입에 필드만 추가하면 API 레이어는 거의 바뀌지 않는다. 변경이 필요한 곳은 `NotesContext.createNote`의 인자(현재 `title, content`)뿐이다.

- **Decision**: 데이터 구조는 정의서대로 두고, 태그 로직을 **규칙 / 상태 / 표현**으로 분리한다.

  | 계층    | 파일                                                           | 책임                                                                                                                                                      |
  | ------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 타입    | `src/types/note.ts`                                            | `tags?: string[]` 추가, "tags 필드는 아직 없음" 주석 정리                                                                                                 |
  | API     | `src/api/notes.ts`                                             | 타입 변경 외에는 유지                                                                                                                                     |
  | Context | `src/context/NotesContext.tsx`                                 | `createNote`가 `tags`를 받도록 확장 (`updateNote`는 변경 없음)                                                                                            |
  | 규칙    | `src/utils/tags.ts` (신규)                                     | 순수 함수. `validateTag(input, existing)`이 trim, 빈 값, 중복, 길이, 개수 검사를 하고 결과(추가 가능 여부, 정규화된 값, 안내 문구)를 반환                 |
  | 상태    | `src/hooks/useTagEditor.ts` (신규)                             | `tags`, `isInputOpen`, `inputValue`, `errorMessage` 상태와 `toggleInput`, `changeInput`, `addTag`(Enter), `removeTag`, `reset(initialTags)` 동작을 캡슐화 |
  | 표현    | `src/components/Tag.tsx`, `TagInput.tsx`, `TagList.tsx` (신규) | props만 받는 순수 표현 컴포넌트. `Tag`는 정의서 명세(`TagProps`, `onDelete`, `truncate`, `title`) 그대로                                                  |
  | 조립    | `src/components/NoteEditor.tsx`                                | `useTagEditor`를 호출해 `TagInput`/`TagList`를 배치하고, 저장 시 `title`, `content`, `tags`를 함께 전달. 노트 전환 시 기존 `useEffect`에서 `reset` 호출   |
  | 표시    | `src/components/NoteItem.tsx`                                  | `note.tags ?? []`의 길이로 아이콘과 개수 표시                                                                                                             |
  - 구현 순서는 정의서의 "타입 → API → Context → 컴포넌트"를 유지하되, 4~5단계를 `utils/tags.ts` → `Tag` → `TagInput`/`TagList` → `useTagEditor` → `NoteEditor`로 쪼갠다.
  - 서버 저장은 기존 패턴대로 저장 버튼에서만 하고, 응답 후 Context 배열을 갱신한다(재조회 없음).

- **Alternatives**:
  - **A안: 인라인** — 로직을 모두 `NoteEditor`에 둔다. 변경이 가장 적고 기존 패턴과 가장 일치하지만, 규칙 7개를 UI를 거쳐야만 테스트할 수 있고 `NoteEditor`가 폼 동기화, 저장, 태그 규칙을 모두 떠안는다.
  - **C안: 별도 리소스** — `/tags` 리소스와 `Note.tagIds`로 정규화하고 `TagsContext`를 추가한다. 이름 변경, 집계 등에 유리하지만, `db.json` 수정(정의서와 충돌), 노트 저장 시 API 2회 호출과 부분 실패 처리, Context 2개 유지가 필요하다. 현재 Out of Scope 항목(태그 관리, 필터 등)을 전제로 한 과설계다.

- **Consequences**:
  - (+) 검증 규칙을 렌더링 없이 단위 테스트한다. 훅은 `renderHook`, 표현 컴포넌트는 props만으로 테스트하고, `NoteEditor` 테스트는 통합 시나리오에 집중한다.
  - (+) 규칙(길이, 개수) 변경이 `utils/tags.ts` 한 곳에서 끝나고, 이후 필터/자동완성은 `notes`에서 파생해 붙일 수 있다.
  - (+) 데이터·API·Context 변경은 A안과 같아서 `db.json` 호환(`note.tags ?? []`)과 정의서 확정 사항을 그대로 지킨다.
  - (−) `src/utils/`, `src/hooks/`라는 새 디렉터리와 커스텀 훅 패턴이 생긴다. `CLAUDE.md` 아키텍처 섹션과 `spec-fixed.md` 구현 순서에 반영해야 한다.
  - (−) 파일 수가 늘어(신규 6개) 이번 규모에서는 구조가 다소 무겁다.
  - (−) 태그 이름 변경처럼 모든 노트를 순회해야 하는 기능은 이 구조에서도 쉽지 않다. 필요해지면 C안으로의 전환을 새 ADR로 다룬다.

### ADR-002: 컴포넌트 개발 원칙 — 상태 / 훅 / 구조 분리

- **Status**: 확정 (태그 기능을 시작으로 이후 컴포넌트에도 적용)

- **Context**:
  - 현재 `NoteEditor`는 폼 상태, 동기화 이펙트, 저장 로직, 마크업이 한 파일에 있고, 동기화 `useEffect`에는 `eslint-disable-line react-hooks/exhaustive-deps`가 붙어 있다.
  - 태그 기능을 인라인으로 넣으면 이 파일이 더 커지고 테스트하기 어려워진다.
  - 앞으로도 컴포넌트가 계속 추가될 예정이라, 기능마다 구조를 새로 정하면 일관성과 확장성이 떨어진다.

- **Decision**: 새 컴포넌트와 기능은 다음 기준으로 분리해서 개발한다.
  - **규칙(순수 로직)**: 검증, 변환 등 상태가 없는 로직은 `src/utils/<이름>.ts`의 순수 함수로 둔다.
  - **상태 + 동작**: 컴포넌트 로컬 상태와 그에 딸린 동작이 둘 이상이면 `src/hooks/use<이름>.ts` 커스텀 훅으로 뺀다.
  - **표현**: UI 조각은 props만 받는 순수 컴포넌트로 나눈다. 데이터 호출(`useNotes()`)은 최상위 조립 컴포넌트에서만 한다.
  - **네이밍**: 훅은 `useXxx.ts`(camelCase), 컴포넌트는 기존대로 `PascalCase.tsx` + named export, 파일명과 export명 일치.
  - 외부 상태관리 라이브러리는 도입하지 않는다(기존 `useState` + Context 유지).

- **Alternatives**:
  - 기능별로 필요할 때만 분리(현행 방식): 단순하지만 기준이 사람마다 달라진다.
  - 폴더를 기능 단위로 재구성(`features/tag/...`): 확장성은 높지만 지금 규모에는 과하고 기존 구조(`components/`, `context/`, `api/`, `types/`)와 충돌한다.

- **Consequences**:
  - (+) 컴포넌트 단위로 테스트와 교체가 쉽고, 새 기능도 같은 틀로 만든다.
  - (−) 작은 컴포넌트까지 분리하면 파일이 과도하게 늘 수 있다. "상태/동작이 둘 이상이거나 규칙이 둘 이상일 때만 분리"를 기준으로 판단한다.
  - (−) 기존 컴포넌트(`NoteEditor`의 `title`/`content`)는 이번 범위에서 리팩터링하지 않고, 해당 영역을 수정할 때 점진적으로 맞춘다.

## 5. Out of Scope

이번 범위에 포함하지 않는 항목이다. 필요해지면 별도 기능으로 기획한다.

### 태그 활용 기능

- 태그로 노트 필터링 (특정 태그를 가진 노트만 보기)
- 태그 기반 검색, 자동완성, 입력 중 추천
- 태그 클릭 시 동작 (태그 클릭으로 필터/이동)
- 인기 태그, 태그별 노트 개수 같은 통계/집계
- 전체 태그 목록 화면, 태그 관리 페이지

### 태그 자체 관리

- 태그 이름 수정 (삭제 후 재추가로만 변경)
- 태그 일괄 삭제, 전체 삭제 버튼
- 태그 순서 변경 (드래그 앤 드롭 등). 추가한 순서만 유지한다
- 여러 노트에 걸친 태그 일괄 이름 변경/병합
- 태그 색상 지정, 태그별 아이콘 커스터마이즈
- 태그 계층(상위/하위), 태그 그룹

### 입력/동작

- 쉼표·공백 등 구분자로 여러 태그 한 번에 입력 (Enter로 한 개씩만 추가)
- 태그 입력 시 특수문자 제한 및 정규화(소문자 변환, `#` 자동 처리 등). 특수문자는 제한하지 않는다
- 붙여넣기 시 여러 태그로 분리
- 태그 추가/삭제의 즉시 서버 반영 (저장 버튼으로만 반영)
- 미저장 변경에 대한 이탈 확인창 (노트 전환 시 조용히 버린다)
- 실행 취소/다시 실행(undo/redo)

### UI

- 터치 기기에서 삭제 버튼 항상 표시 (이번에는 hover/focus 시에만 표시)
- NoteItem에서 태그 이름 직접 표시 (아이콘과 개수만 표시)
- 편집 중 미저장 태그 개수를 NoteItem에 실시간 반영 (서버 저장값 기준)
- 모바일/반응형 전용 레이아웃 최적화
- 다크 모드 등 테마별 별도 태그 스타일

### 데이터/서버

- `db.json` 기존 노트 데이터 마이그레이션 (`tags`가 없는 노트는 `?? []`로 처리)
- 태그를 별도 리소스(`/tags`)로 분리하거나 서버 측 태그 유효성 검증
- 낙관적 업데이트, 저장 후 재조회(refetch). 기존 패턴(서버 응답 후 로컬 갱신)을 유지한다
- 다중 사용자, 태그 공유, 권한 관리
- 서버 장애 시 재시도, 오프라인 지원

### 기타

- 태그 내보내기/가져오기
- 태그 변경 이력 관리
- 접근성 고도화 (삭제 버튼 `aria-label` 및 키보드 포커스 표시 이외의 스크린리더 안내 개선)
- 다국어 지원 (UI 문구는 한국어로 통일)

## 6. 용어 정의

| 용어                      | 정의                                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 태그 (Tag)                | 노트에 붙이는 문자열 라벨. 노트의 `tags: string[]`에 추가한 순서대로 저장한다.                              |
| `Tag` 컴포넌트            | 태그 하나를 표시하는 순수 표현 컴포넌트(`src/components/Tag.tsx`). 아이콘, 라벨, 삭제 버튼으로 구성한다.    |
| `TagProps`                | `Tag` 컴포넌트의 props 인터페이스.                                                                          |
| NoteEditor                | 노트 상세/편집 화면(메인 영역). 제목/내용/태그를 편집하고 생성·수정을 겸한다.                               |
| NoteItem                  | 왼쪽 노트 목록의 카드 컴포넌트. 태그가 있으면 아이콘과 개수를 표시한다.                                     |
| "태그 추가" / "닫기" 버튼 | 태그 입력창을 열고 닫는 토글 버튼. 입력창이 열리면 "닫기"로 바뀐다.                                         |
| 태그 입력창               | Enter로 태그를 한 개씩 추가하는 입력 필드. 추가 후에도 열린 상태를 유지한다.                                |
| 로컬 `tags` state         | NoteEditor가 가진 편집 중 태그 배열. "저장" 전까지 서버에 반영되지 않는다.                                  |
| 중복 판정                 | trim 후 대소문자를 무시하고 비교한다. 저장은 처음 입력한 표기 그대로 한다.                                  |
| trim                      | 입력값 앞뒤 공백 제거.                                                                                      |
| 옵셔널 필드               | `tags?`처럼 없을 수도 있는 필드. 기존 노트는 `note.tags ?? []`로 처리한다.                                  |
| 노트 전환                 | `selectedNoteId` 또는 `isCreating`이 바뀌는 것. 이때 `title`, `content`, `tags`와 입력창 상태가 리셋된다.   |
| ADR                       | Architecture Decision Record. Context / Decision / Alternatives / Consequences로 기술 결정을 기록하는 형식. |
| PRD                       | Product Requirements Document. 기능의 배경, 사용자, 요구사항, 범위를 정리한 문서.                           |
