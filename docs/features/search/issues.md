# 검색 기능 이슈 목록 (수직 슬라이싱)

> 기준 문서: [`prd.md`](./prd.md), [`spec-fixed.md`](./spec-fixed.md) (확정본), 구조 결정은 `prd.md`의 ADR-001을 따른다. 수직 슬라이싱 원칙으로 분해했다. 각 이슈는 타입 → 규칙(`utils`) → 표현(컴포넌트) → 조립 → 상태 연결을 필요한 만큼만 관통해, 단독으로 동작하고 테스트하고 시연할 수 있다. 레이어별로 나눈 버전은 [`horizon_issues.md`](./horizon_issues.md)를 참고한다.

## 이슈 요약

| #   | 제목                                                       | 의존          |
| --- | ---------------------------------------------------------- | ------------- |
| 1   | 검색어로 노트를 찾고 해제한다 (워킹 스켈레톤)              | 없음          |
| 2   | 검색 대상을 전체/제목/내용으로 고른다                      | #1            |
| 3   | 태그로 노트를 검색한다                                     | #2, 태그 기능 |
| 4   | 검색 결과 건수와 안내 문구를 보여주고 노트 변경을 반영한다 | #1            |

#2와 #4는 #1 완료 후 서로 독립적이라 병렬 진행이 가능하다. #3은 #2의 선택박스에 의존한다.

## 공통 사항

- TDD로 진행한다. 규칙은 `utils` 단위 테스트, 컴포넌트는 props 기반 테스트, 조립과 `App`은 통합 테스트(`api` mock 또는 `NotesProvider`)로 검증한다.
- 구조는 ADR-001을 따른다: 필터 규칙은 `utils/searchNotes.ts`의 순수 함수, `SearchBar`는 로컬 상태(선택박스 값, 입력 텍스트)와 `onSearch`, 확정 조건은 `App`의 `useState`, `useNotes()` 호출은 조립 컴포넌트 `NoteSidebar`에서만 한다. `NotesContext`와 `api/`는 변경하지 않는다.
- 목록과 건수는 별도 저장 없이 `notes`와 확정 조건에서 렌더링마다 파생한다.
- 검색은 Enter 또는 검색 버튼에서만 적용된다. 실시간(타이핑 중) 필터링은 하지 않는다.
- UI 문구는 한국어, 입력 요소(`select`, `input`)에는 `aria-label`을 단다.
- 선행 조건: 태그 검색(#3)은 태그 기능의 `Note.tags?: string[]`가 먼저 반영되어 있어야 한다. 태그가 없는 기존 노트는 `note.tags ?? []`로 처리한다.
- 이번 범위는 정의서 기준이며, 최근 검색어 저장(ADR-002)은 정의서에 UI/규칙이 없어 다루지 않는다.

## 이슈 1. 검색어로 노트를 찾고 해제한다 (워킹 스켈레톤)

### 설명

사이드바 상단의 검색창에 검색어를 입력하고 Enter 또는 검색 버튼을 누르면, 제목 또는 내용에 검색어가 포함된 노트만 목록에 남는다. 검색어를 비우고 다시 검색하면 필터가 해제되어 전체 목록으로 돌아온다. 이 핵심 경로를 end-to-end로 만든다. 이후 이슈의 기반이다. 검색 조건 타입, 필터 규칙(`utils/searchNotes.ts`), `SearchBar`(입력창과 검색 버튼), `NoteSidebar` 조립, `NoteList`가 결과를 표시하는 구조, `App`의 확정 조건 상태를 함께 만든다.

### 완료조건 (Acceptance Criteria)

- [ ] 사이드바(노트 목록) 상단에 검색창이 있고, 한 줄(`flex`)에 입력창과 검색 버튼이 배치된다.
- [ ] 입력창: placeholder "검색어를 입력하세요", `aria-label="검색어"`, `min-w-0 flex-1`.
- [ ] 검색 버튼: 돋보기 아이콘만 표시(텍스트 없음), `aria-label="검색"`, `cursor-pointer hover:opacity-75`.
- [ ] 입력창에서 Enter 또는 검색 버튼을 누르면 제목 또는 내용에 검색어가 포함된 노트만 목록에 표시된다.
- [ ] 검색어는 앞뒤 공백을 trim하고 대소문자를 무시하여 부분 일치(`includes`)로 비교한다.
- [ ] 일치한 노트는 기존 노트 순서를 유지한다(정렬 없음).
- [ ] 타이핑만 하고 Enter/검색 버튼을 누르지 않으면 목록은 바뀌지 않는다.
- [ ] trim 후 검색어가 비어 있으면 필터를 적용하지 않고 전체 노트를 기존 순서대로 보여준다.
- [ ] 지우기(x) 버튼과 초기화 버튼은 없다. 입력창을 비우고 Enter(또는 검색 버튼)를 누르는 것이 필터 해제 방법이다.
- [ ] 검색 조건을 바꿔도 `selectedNoteId`와 `isCreating`은 변하지 않는다(편집 화면 유지).

### Given / When / Then

**시나리오 1-1. 제목으로 찾기**

- Given: 제목이 `React 노트`, `Vue 노트`인 노트가 목록에 있다.
- When: 입력창에 `react`를 입력하고 Enter를 누른다.
- Then: `React 노트`만 목록에 남는다(대소문자 무시).

**시나리오 1-2. 내용으로 찾기, 공백 trim**

- Given: 내용에만 `hook`이 들어간 노트와 어디에도 없는 노트가 있다.
- When: 입력창에 `  HOOK  `을 입력하고 Enter를 누른다.
- Then: 내용에 `hook`이 있는 노트만 기존 순서대로 남는다.

**시나리오 1-3. 검색 버튼으로 찾기**

- Given: 노트 여러 개가 목록에 있다.
- When: 입력창에 검색어를 입력하고 검색 버튼을 클릭한다.
- Then: Enter를 눌렀을 때와 같은 결과로 필터링된다.

**시나리오 1-4. 타이핑만으로는 바뀌지 않음**

- Given: 노트 여러 개가 목록에 있다.
- When: 입력창에 글자를 입력하지만 Enter와 검색 버튼은 누르지 않는다.
- Then: 목록은 그대로이다.

**시나리오 1-5. 비우고 Enter로 해제**

- Given: `react`로 검색해 필터가 적용되어 있다.
- When: 입력창을 비우고 Enter를 누른다.
- Then: 전체 노트가 기존 순서대로 표시된다.

**시나리오 1-6. 공백만 입력해 해제**

- Given: `react`로 검색해 필터가 적용되어 있다.
- When: 입력창에 공백만 입력하고 검색 버튼을 누른다.
- Then: 전체 노트가 기존 순서대로 표시된다.

**시나리오 1-7. 처음부터 빈 검색어**

- Given: 필터가 적용되지 않은 초기 상태이다.
- When: 입력창을 비운 채 Enter를 누른다.
- Then: 목록은 전체 노트 그대로이다.

**시나리오 1-8. 검색해도 편집 화면 유지**

- Given: 노트 A를 선택해 편집 중이다.
- When: 노트 A와 일치하지 않는 검색어로 검색한다.
- Then: 목록에서 노트 A는 사라지지만 편집 화면은 그대로 유지된다.

## 이슈 2. 검색 대상을 전체/제목/내용으로 고른다

### 설명

검색창에 선택박스를 추가해 제목만 또는 내용만으로 검색 범위를 좁힐 수 있게 한다. `SearchBar`의 선택박스 로컬 상태, `onSearch({ field, keyword })`, 필터 규칙의 필드 분기를 함께 확장한다. 태그 옵션은 #3에서 추가한다.

### 완료조건 (Acceptance Criteria)

- [ ] 검색창이 한 줄에 `[선택박스] [입력창] [검색 버튼]` 순서로 배치된다.
- [ ] 선택박스: 옵션 순서 전체 → 제목 → 내용, 기본값 "전체", `aria-label="검색 대상"`, 고정 너비.
- [ ] "제목"은 제목에 검색어가 포함된 노트만, "내용"은 내용에 검색어가 포함된 노트만 일치시킨다.
- [ ] "전체"는 제목 OR 내용 중 하나라도 일치하면 결과에 포함한다.
- [ ] 선택박스만 바꿔서는 필터가 바뀌지 않고, Enter/검색 버튼을 눌렀을 때 선택박스 값과 검색어가 함께 적용된다.
- [ ] 입력 중인 값과 적용된 조건이 어긋나도(선택박스만 바꾼 상태) 목록은 이전 확정 조건을 유지한다.
- [ ] 선택박스 값과 무관하게 빈 검색어는 필터 해제로 처리되며, 해제 후에도 선택박스 값은 유지된다.

### Given / When / Then

**시나리오 2-1. 제목만 검색**

- Given: 제목에 `hook`이 있는 노트 A, 내용에만 `hook`이 있는 노트 B가 있다.
- When: 선택박스를 "제목"으로 바꾸고 `hook`을 입력해 Enter를 누른다.
- Then: 노트 A만 목록에 남는다.

**시나리오 2-2. 내용만 검색**

- Given: 제목에 `hook`이 있는 노트 A, 내용에만 `hook`이 있는 노트 B가 있다.
- When: 선택박스를 "내용"으로 바꾸고 `hook`을 입력해 Enter를 누른다.
- Then: 노트 B만 목록에 남는다.

**시나리오 2-3. 전체 검색**

- Given: 제목에 `hook`이 있는 노트 A, 내용에만 있는 노트 B, 어디에도 없는 노트 C가 있다.
- When: 선택박스를 "전체"로 두고 `hook`을 입력해 Enter를 누른다.
- Then: 노트 A, B가 기존 순서대로 남고 C는 제외된다.

**시나리오 2-4. 선택박스 변경만으로는 적용되지 않음**

- Given: "전체", `hook`으로 검색해 노트 A, B가 표시되어 있다.
- When: 선택박스를 "제목"으로 바꾸기만 한다(Enter/버튼은 누르지 않는다).
- Then: 목록은 노트 A, B 그대로이고, 검색 버튼을 누르면 노트 A만 남는다.

**시나리오 2-5. 해제해도 선택박스 값 유지**

- Given: 선택박스 "제목", 검색어 `react`로 필터가 적용되어 있다.
- When: 입력창을 비우고 Enter를 누른다.
- Then: 전체 노트가 표시되고, 선택박스는 "제목"으로 유지된다.

## 이슈 3. 태그로 노트를 검색한다

### 설명

선택박스에 "태그" 옵션을 추가하고, "전체" 검색에도 태그를 포함한다. 필터 규칙(`note.tags ?? []`), 선택박스 옵션, 조립 결과가 함께 바뀐다. 태그 기능(`Note.tags`)이 먼저 반영되어 있어야 한다.

### 완료조건 (Acceptance Criteria)

- [ ] 선택박스 옵션 순서가 전체 → 제목 → 내용 → 태그가 된다.
- [ ] "태그"는 노트의 태그 중 하나라도 검색어를 포함하면 일치한다(trim, 대소문자 무시, 부분 일치).
- [ ] "전체"는 제목 OR 내용 OR 태그 중 하나라도 일치하면 결과에 포함한다.
- [ ] `tags`가 없는 기존 노트는 `note.tags ?? []`로 처리하며, 어떤 검색 대상에서도 에러가 나지 않는다.
- [ ] 태그가 없는 노트는 "태그" 검색 결과에서 제외된다.

### Given / When / Then

**시나리오 3-1. 태그로 검색**

- Given: `tags: ['React', 'design']`인 노트 A와 `tags: ['vue']`인 노트 B가 있다.
- When: 선택박스를 "태그"로 바꾸고 `rea`를 입력해 Enter를 누른다.
- Then: 노트 A만 목록에 남는다(태그 중 하나라도 부분 일치).

**시나리오 3-2. 전체 검색에 태그 포함**

- Given: 제목에만 `hook`이 있는 노트 A, 내용에만 있는 노트 B, 태그에만 있는 노트 C, 어디에도 없는 노트 D가 있다.
- When: "전체"로 `hook`을 검색한다.
- Then: 노트 A, B, C가 기존 순서대로 남고 D는 제외된다.

**시나리오 3-3. 태그가 없는 기존 노트**

- Given: `tags` 필드가 없는 기존 노트와 태그가 있는 노트가 섞여 있다.
- When: "태그"로 검색한 뒤 "전체"로 다시 검색한다.
- Then: 에러 없이 동작하고, 태그가 없는 노트는 "태그" 결과에서 제외된다("전체"에서는 제목/내용으로만 판단된다).

## 이슈 4. 검색 결과 건수와 안내 문구를 보여주고 노트 변경을 반영한다

### 설명

검색 결과를 사용자에게 알려주는 세 가지를 함께 다룬다. 검색창 하단 좌측에 "검색 결과 N건"을 표시하고, 노트가 아예 없는 경우와 검색 결과가 0건인 경우를 서로 다른 문구로 구분하며, 필터가 걸린 상태에서 노트를 생성/수정/삭제해도 조건이 유지되고 목록과 건수가 다시 계산되게 한다. `NoteSidebar`가 결과 길이를 `SearchBar`에 전달하고, `NoteList`가 결과와 전체 노트 존재 여부로 분기한다. 검색어 유무를 판단하는 `hasSearchKeyword`(trim 후 비어 있는지)를 이 이슈에서 도입한다.

### 완료조건 (Acceptance Criteria)

- [ ] 확정된 검색어가 있을 때(trim 후 비어 있지 않을 때)만 "검색 결과 N건"을 표시한다. 필터가 없거나 해제된 상태에서는 표시하지 않는다.
- [ ] 결과가 0건이어도 "검색 결과 0건"을 표시한다.
- [ ] 건수 문구는 검색창 하단 좌측에 `text-muted-foreground` 작은 글씨로 표시한다.
- [ ] N은 `notes`에서 확정 조건으로 걸러낸 개수이며 목록에 표시된 노트 수와 항상 같다. 타이핑만 한 상태에서는 건수가 바뀌지 않는다.
- [ ] `NoteList`의 early return 순서는 `loading` → `error` → 노트 없음 → 검색 결과 없음 → 본문이다.
- [ ] 전체 노트가 하나도 없으면 "노트가 없습니다"를, 노트는 있으나 필터 결과가 0건이면 "검색 결과가 없습니다"를 표시하며 두 문구는 섞이지 않는다. 로딩 중이거나 에러가 있을 때는 빈 목록 문구를 표시하지 않는다.
- [ ] 필터가 걸린 상태에서 노트를 생성, 수정, 삭제해도 검색 조건과 검색창의 입력 값은 바뀌지 않고, 목록과 건수는 변경된 `notes`와 같은 확정 조건에서 다시 계산된다.
- [ ] 저장 후 조건에 맞지 않게 된 노트는 목록에서 사라지지만, 편집 화면은 닫히거나 바뀌지 않고 그대로 유지된다. 조건에 맞는 새 노트만 목록에 나타난다.

### Given / When / Then

**시나리오 4-1. 건수 표시**

- Given: 노트 5개 중 제목 또는 내용에 `react`가 있는 노트가 3개이다.
- When: `react`로 검색한다.
- Then: 목록에 3개가 표시되고 검색창 하단 좌측에 "검색 결과 3건"이 표시된다.

**시나리오 4-2. 검색 결과 없음**

- Given: 노트가 여러 개 있고 어떤 노트에도 `zzz`가 없다.
- When: `zzz`로 검색한다.
- Then: "검색 결과가 없습니다"와 "검색 결과 0건"이 표시되고 "노트가 없습니다"는 표시되지 않는다.

**시나리오 4-3. 노트가 없음**

- Given: 저장된 노트가 하나도 없다.
- When: 앱을 연다.
- Then: 사이드바에 "노트가 없습니다"가 표시되고 "검색 결과가 없습니다"와 건수 문구는 표시되지 않는다.

**시나리오 4-4. 해제하면 건수가 사라지고 목록이 돌아옴**

- Given: "검색 결과 3건"(또는 "검색 결과가 없습니다")이 표시되어 있다.
- When: 입력창을 비우고 Enter를 누른다.
- Then: 건수 문구가 사라지고 전체 노트 목록이 다시 표시된다.

**시나리오 4-5. 타이핑만으로는 건수가 바뀌지 않음**

- Given: "검색 결과 3건"이 표시되어 있다.
- When: 입력창에 다른 검색어를 입력하지만 Enter는 누르지 않는다.
- Then: 건수는 "검색 결과 3건" 그대로이다.

**시나리오 4-6. 로딩 중**

- Given: 노트 목록을 불러오는 중이다.
- When: 사이드바를 렌더링한다.
- Then: 로딩 표시만 나타나고 빈 목록 문구는 나타나지 않는다.

**시나리오 4-7. 삭제 후 조건 유지**

- Given: `react` 검색으로 노트 2건이 표시되어 있다.
- When: 그중 한 노트를 삭제한다.
- Then: 검색 조건은 유지된 채 목록은 1건이 되고, 건수 문구는 "검색 결과 1건"이 된다.

**시나리오 4-8. 수정으로 조건 밖이 된 노트**

- Given: `react` 검색 결과에 있는 노트를 열어 편집 중이다.
- When: 제목에서 `react`를 지우고(내용에도 `react`가 없다) 저장한다.
- Then: 해당 노트는 목록에서 사라지고 건수가 줄지만, 편집 화면은 그대로 열려 있다.

**시나리오 4-9. 새 노트 생성**

- Given: `react` 검색이 적용되어 있다.
- When: 제목에 `react`가 들어간 새 노트와, 들어가지 않은 새 노트를 각각 저장한다.
- Then: 제목에 `react`가 있는 노트만 목록에 나타나고 건수가 1 늘어난다.

## 확인이 필요한 항목

- **`NoteList` 구조 차이**: `spec-fixed.md`는 `NoteList`가 조건을 받아 직접 필터링한다고 쓰고, ADR-001은 `NoteSidebar`가 필터링하고 `NoteList`는 결과를 받아 표시하도록 정했다. 이 문서는 ADR-001을 따랐다. 정의서의 UI 명세와 구현 순서도 ADR-001에 맞게 정리가 필요하다.
- **스타일 기준**: 정의서는 `border-border`, `bg-card` 같은 기존 시맨틱 토큰을 쓰라고 하지만, 디자인 시스템은 영역 구분 테두리 금지(No-Line)와 입력창은 포커스 때만 `tertiary`로 바꾸는 규칙을 둔다. #1, #2 구현 시 어느 기준을 따를지 확정이 필요하다.

## Out of Scope

`prd.md`의 4번(Out of Scope)을 따른다. 실시간 필터링, 일치 필드별 정렬과 하이라이트, 지우기/초기화 버튼, 서버 측 검색, 검색 조건 영속화 등은 이슈로 만들지 않는다.
