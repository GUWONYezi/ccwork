# 노트 검색 기능 PRD

> 기준 문서: [`spec-fixed.md`](./spec-fixed.md) (확정본). 3번(기술 결정)은 ADR-001(검색 아키텍처), ADR-002(최근 검색어 저장)로 확정했다.

## 1. 컴포넌트 개요 (요약과 배경)

### 요약

왼쪽 노트 목록 상단에 검색창(`SearchBar`)을 두고, 검색 대상(전체/제목/내용/태그)과 검색어를 지정해 노트 목록을 필터링하는 기능이다. Enter 또는 검색 버튼을 눌렀을 때만 조건이 확정되며(실시간 필터링 없음), 확정된 조건으로 `NoteList`가 `notes`에서 결과를 파생해 보여준다. 검색 결과 건수는 검색창 하단에 "검색 결과 N건"으로 표시한다.

### 배경 및 근거

- 현재는 노트가 늘어나도 원하는 노트를 찾으려면 목록을 눈으로 훑어야 한다. 제목·내용·태그를 모두 가진 노트가 쌓일수록 탐색 비용이 커진다.
- 태그 기능(`docs/features/tag/prd.md`)으로 `Note.tags`가 생기면 "태그로 찾기"가 자연스러운 다음 단계가 된다. 태그 PRD는 필터링/검색을 Out of Scope로 남겨두었고, 이 기능이 그 후속이다.
- 검색은 서버 호출 없이 이미 불러온 `notes`를 걸러내는 클라이언트 측 변경이라 범위가 작다. 필터 규칙은 순수 함수로 분리해 TDD로 연습하기에 적합하다.

### 기획 및 개발의 중요성

- **기획**: 검색 시점(Enter/버튼으로만 확정), 선택박스 변경 시 동작(필터 유지), 빈 검색어 처리(필터 해제), 건수 문구 표시 조건을 먼저 확정하지 않으면 UI와 테스트 기준이 흔들린다. 그래서 정의서에서 질의응답 10개로 규칙을 확정했다.
- **개발**:
  - 태그가 없는 기존 노트(`tags` 없음)에서 에러가 나지 않아야 한다(`note.tags ?? []`).
  - 입력 중인 값(`SearchBar` 로컬 state)과 확정된 조건(`App` state)이 의도적으로 어긋날 수 있다. 두 상태의 경계를 명확히 해야 한다.
  - 목록은 `notes`와 확정 조건에서 매번 파생한다. 노트를 생성/수정/삭제해도 필터가 유지되고 건수도 함께 바뀌어야 한다.
  - "노트가 없습니다"와 "검색 결과가 없습니다"를 구분해야 한다.
- **선행 조건**: 태그 검색을 검증하려면 `Note.tags?: string[]`가 먼저 반영되어 있어야 한다.

## 2. 사용자 스토리

### 개인 노트 작성자

- 노트 작성자로서, 검색어를 입력해 노트를 찾고 싶다. 그래야 목록을 일일이 훑지 않고도 원하는 노트에 바로 갈 수 있다.
- 노트 작성자로서, 제목/내용/태그 중 검색 대상을 고르고 싶다. 그래야 "제목에만 있는 단어"처럼 범위를 좁혀 정확히 찾을 수 있다.
- 노트 작성자로서, 대상을 "전체"로 두고 검색하고 싶다. 그래야 어디에 적었는지 기억나지 않아도 찾을 수 있다.
- 노트 작성자로서, "검색 결과 N건"을 보고 싶다. 그래야 검색이 얼마나 걸러졌는지 바로 알 수 있다.
- 노트 작성자로서, 결과가 없을 때 "검색 결과가 없습니다"를 보고 싶다. 그래야 노트가 없는 것인지 검색 결과가 없는 것인지 구분할 수 있다.

### 빠른 검색을 하는 사용자

- 키보드 사용자로서, 입력창에서 Enter만으로 검색하고 싶다. 그래야 마우스 없이 검색할 수 있다.
- 검색 사용자로서, 대소문자와 앞뒤 공백을 신경 쓰지 않고 검색하고 싶다. 그래야 정확한 표기를 기억하지 못해도 찾을 수 있다.
- 검색 사용자로서, 입력창을 비우고 Enter를 눌러 필터를 해제하고 싶다. 그래야 별도의 초기화 버튼 없이 전체 목록으로 돌아올 수 있다.
- 검색 사용자로서, 타이핑하는 동안에는 목록이 바뀌지 않기를 원한다. 그래야 입력 중에 화면이 흔들리지 않는다.
- 검색 사용자로서, 최근에 검색한 검색어 목록을 보고 싶다. 그래야 같은 검색을 다시 입력하지 않아도 된다.
- 검색 사용자로서, 최근 검색어를 개별로 또는 한 번에 지우고 싶다. 그래야 불필요한 기록을 정리할 수 있다.
- 검색 사용자로서, 새로고침 후에도 최근 검색어가 남아 있길 원한다. 그래야 반복 검색이 편하다.

### 검색 중 노트를 편집하는 사용자

- 노트 작성자로서, 검색한 상태에서 노트를 수정/삭제/생성해도 검색 조건이 유지되길 원한다. 그래야 같은 검색을 반복하지 않고 작업을 이어갈 수 있다.
- 노트 작성자로서, 저장 후 검색 조건에 맞지 않게 된 노트가 목록에서 사라져도 편집 화면은 그대로이길 원한다. 그래야 편집하던 흐름이 끊기지 않는다.

### 기존 노트 사용자

- 기존 노트 사용자로서, 태그가 없는 예전 노트도 검색 대상에 포함되길 원한다. 그래야 데이터 마이그레이션 없이 기존 노트를 계속 찾을 수 있다.

## 3. 기술 결정 (ADR)

### ADR-001: 검색 아키텍처 — 순수 필터 함수 + 조립 컴포넌트 (B안)

- **Status**: 확정

- **Context**:
  - 정의서(`spec-fixed.md`)가 확정한 것: 확정 조건은 `App`의 `useState`, 입력 중인 값은 `SearchBar` 로컬 state, `NotesContext`에는 검색 상태를 두지 않는다.
  - `App`은 `NotesProvider`를 감싸는 쪽이라 `useNotes()`를 호출할 수 없다. 그런데 "검색 결과 N건"은 `SearchBar` 아래에 표시되므로 `notes`에서 계산한 값이 필요하다. 건수를 어디서 계산해 전달할지가 핵심 쟁점이다.
  - 목록 필터와 건수가 같은 규칙에서 나와야 하고(trim, 대소문자 무시, 태그 없는 기존 노트는 `tags ?? []`), 프로젝트는 TDD로 진행하므로 규칙을 렌더링 없이 검증할 수 있어야 한다.
  - 태그 PRD의 ADR-002(컴포넌트 개발 원칙)는 규칙 / 상태 / 표현 분리와, `useNotes()` 호출을 최상위 조립 컴포넌트에서만 하는 것을 원칙으로 정했다.

- **Decision**: 규칙, 상태, 표현, 조립을 다음과 같이 나눈다.

  | 계층             | 파일                                    | 책임                                                                                                                   |
  | ---------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
  | 타입             | `src/types/search.ts` (신규)            | `SearchField`(`all`/`title`/`content`/`tag`), `SearchCondition`(`field`, `keyword`)                                    |
  | 규칙             | `src/utils/searchNotes.ts` (신규)       | `filterNotes(notes, condition)` 순수 함수. trim, 대소문자 무시, 부분 일치, `note.tags ?? []`, 빈 검색어면 전체 반환    |
  | 상태 (확정 조건) | `src/App.tsx`                           | `condition`을 `useState`로 보관하고 `NoteSidebar`로 내려보낸다                                                         |
  | 상태 (입력 중)   | `src/components/SearchBar.tsx` (신규)   | 선택박스/입력창 로컬 `useState`. Enter/검색 버튼 시 `onSearch({ field, keyword })`                                     |
  | 조립             | `src/components/NoteSidebar.tsx` (신규) | `useNotes()`를 한 번 호출하고, `filterNotes`로 목록과 건수를 같은 결과에서 계산해 `SearchBar`와 `NoteList`에 전달      |
  | 표현             | `src/components/NoteList.tsx`           | 필터된 목록을 props로 받아 렌더링. "노트가 없습니다"(전체 `notes` 없음)와 "검색 결과가 없습니다"(필터 결과 0건)를 구분 |
  - `NotesContext`와 `api/`는 변경하지 않는다. 목록과 건수는 별도 저장 없이 `notes`와 확정 조건에서 렌더링마다 파생한다(memo 계열 훅 없음).
  - 구현 순서: 타입 → `filterNotes` → `SearchBar` → `NoteSidebar` → `App` 연결 → `NoteList` 수정.

- **Alternatives**:
  - **A안: 인라인** — 필터를 `NoteList` 안에 쓰고 `SearchBar`가 건수를 위해 `useNotes()`를 직접 호출한다. 파일이 가장 적지만 필터 규칙이 목록과 건수 두 곳에 중복되고, 규칙 검증이 렌더링을 거쳐야 하며, `SearchBar`가 표현 컴포넌트 성격을 잃는다.
  - **C안: Context 확장** — `NotesContext`에 `condition`, `filteredNotes`, `resultCount`를 둔다. 건수 문제는 가장 쉽게 풀리고 "태그 클릭 → 검색" 같은 전역 연동에 유리하다. 하지만 정의서의 "NotesContext에는 검색 상태를 두지 않는다"와 충돌하고, UI 상태가 Context로 들어가 "UI 선택 상태는 `App`" 패턴이 깨지며, 조건이 바뀔 때마다 소비자 전체가 리렌더링된다.
  - (참고) 서버 측 검색(`json-server` 쿼리)은 이미 불러온 `notes`로 충분하고 건수 계산 방식도 달라져서 검토 대상에서 제외했다.

- **Consequences**:
  - (+) 필터 규칙이 한 곳에 있어 목록과 건수가 항상 일치하고, 필드 추가나 정렬 변경도 `searchNotes.ts` 한 곳에서 끝난다.
  - (+) `filterNotes`는 단위 테스트, `SearchBar`는 props 기반 테스트, `NoteSidebar`는 통합 테스트로 나뉘어 TDD에 맞다. 태그 없는 기존 노트 케이스도 순수 함수에서 바로 검증한다.
  - (+) 정의서의 상태 위치(`App` + 로컬)와 "NotesContext 무수정"을 그대로 지킨다.
  - (−) 새 조립 컴포넌트 `NoteSidebar`가 생기고, `NoteList`의 `useNotes()` 호출이 `NoteSidebar`로 옮겨가는 변경이 필요하다. `CLAUDE.md`의 "데이터가 필요한 컴포넌트(`NoteList`)는 `useNotes()`를 직접 호출" 서술과 아키텍처 트리를 구현 시점에 갱신해야 한다.
  - (−) 검색 조건을 여러 화면에서 공유해야 하는 기능(예: 태그 클릭 → 검색)이 생기면 `App`에서 props로 내려야 해 불편하다. 그 시점에 Context 승격(C안)을 새 ADR로 다룬다.

### ADR-002: 최근 검색어 저장 — `localStorage` + 커스텀 훅 (B안)

- **Status**: 확정

- **Context**:
  - 최근 검색어는 새로고침 후에도 남아야 쓸모가 있다. 이 앱은 인증/다중 사용자가 없는 로컬 단일 사용자용이라 기기 간 공유 요구가 없다.
  - 정의서 방침은 `db.json` 무수정, 서버 데이터는 `api/` + Context 경유이다. 최근 검색어는 노트 데이터가 아니라 UI 편의 데이터다.
  - 규칙이 여럿이다: 확정된 검색만 기록, 빈 검색어 제외, `field + keyword` 대소문자 무시 중복, 최신 순, 최대 10개, 개별/전체 삭제. 렌더링 없이 검증할 수 있어야 한다.
  - ADR-001에서 `NoteSidebar`가 조립 계층으로 정해졌다.

- **Decision**: 규칙은 순수 함수, 상태와 저장은 커스텀 훅, 표시는 props만 받는 컴포넌트로 나눈다.

  | 계층      | 파일                                    | 책임                                                                                                                                                                                  |
  | --------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 타입      | `src/types/search.ts`                   | `RecentSearch { field, keyword, searchedAt }` 추가                                                                                                                                    |
  | 규칙      | `src/utils/recentSearches.ts` (신규)    | `addRecentSearch(list, entry, max)`(빈 값 무시, 중복 제거 후 맨 앞 추가, 개수 제한), `removeRecentSearch`, `parseRecentSearches`(잘못된 JSON·스키마 불일치는 빈 배열)                 |
  | 상태+저장 | `src/hooks/useRecentSearches.ts` (신규) | `useState` 지연 초기화로 `localStorage`(키 `recentSearches`)를 읽고, 변경 시 쓴다. `{ items, add, remove, clear }`를 반환. 읽기/쓰기 예외는 try/catch로 삼키고 메모리 상태는 유지한다 |
  | 조립      | `src/components/NoteSidebar.tsx`        | 훅을 호출하고 `onSearch` 핸들러에서 `add` 후 상위 `onSearch`를 호출. 목록을 `SearchBar`에 props로 전달                                                                                |
  | 표현      | `src/components/SearchBar.tsx`          | 최근 검색어 목록과 `onSelectRecent`/`onRemoveRecent`/`onClearRecent` 콜백을 props로 받아 표시 (노출 방식과 선택 시 동작의 상세는 정의서 보강 때 확정)                                 |
  - 훅 인터페이스를 `{ items, add, remove, clear }`로 고정해, 이후 저장소를 교체해도 호출부가 바뀌지 않게 한다.
  - API 레이어, `NotesContext`, `db.json`은 변경하지 않는다.

- **Alternatives**:
  - **A안: 메모리 state만** — 가장 단순하고 테스트가 쉽지만 새로고침하면 사라져 기능 가치가 크게 떨어진다. 이후 영속화가 필요하면 저장소를 다시 붙여야 한다.
  - **C안: `json-server` 리소스(`/recentSearches`)** — 기기/브라우저 간 공유와 사용자별 기록으로 확장하기 쉽다. 하지만 `db.json` 구조 변경(정의서의 "무수정" 기조와 충돌), `api/` 모듈과 loading/error state 추가, 중복 제거와 개수 제한을 위한 다중 호출과 부분 실패 처리, 테스트 시 `fetch` mock과 `db.json` 초기화가 필요하다. 인증이 없어 공유할 대상도 없다.

- **Consequences**:
  - (+) 서버 변경 없이 새로고침 후에도 유지되고, 동기 접근이라 loading/error state가 필요 없다.
  - (+) 규칙은 순수 함수 단위 테스트, 훅은 `renderHook` + jsdom `localStorage`로 별도 mock 없이 테스트한다. e2e는 `localStorage.clear()`로 초기화가 간단하다.
  - (+) 훅 시그니처를 유지하면 기기 간 동기화가 필요해질 때 훅 내부만 서버 저장으로 교체할 수 있다.
  - (−) 프로젝트에서 처음 쓰는 브라우저 저장소라 파싱 실패, 스키마 변경, 쓰기 실패(용량 초과, 사생활 보호 모드)를 방어하는 코드가 필요하다. 저장 형식이 바뀌면 키 버전 관리나 마이그레이션이 필요해질 수 있다.
  - (−) 브라우저/기기 단위로만 유지되며 다른 브라우저와 공유되지 않는다. 같은 브라우저의 여러 탭 사이에서도 실시간 동기화하지 않는다(`storage` 이벤트 미사용).
  - (−) 최근 검색어 기능이 범위에 들어오므로 `spec-fixed.md`에도 UI/규칙(노출 방식, 최대 개수, 선택 시 동작) 보강이 필요하다.

## 4. Out of Scope

이번 범위에 포함하지 않는 항목이다. 필요해지면 별도 기능으로 기획한다.

### 검색 동작

- 타이핑 중 실시간 필터링, 디바운스 검색
- 선택박스 변경 시 즉시 재검색 (Enter/검색 버튼에서만 적용)
- 일치 필드에 따른 정렬, 관련도 순위, 검색어 하이라이트
- 정규식, 다중 키워드(AND/OR), 따옴표 구문 검색, 초성 검색, 오타 보정
- 검색 자동완성, 검색어 추천 (최근 검색어 기록은 범위 안, ADR-002)

### 검색 대상

- 제목/내용/태그 외 필드 검색 (작성일, 수정일 등)
- 태그 클릭으로 검색 연결 (태그 PRD에서 Out of Scope로 둔 항목)
- 여러 대상을 동시에 고르는 다중 선택 (전체/제목/내용/태그 중 하나만 선택)

### UI

- 지우기(x) 버튼, 별도 초기화 버튼 (입력창을 비우고 Enter로 해제)
- 검색 조건 칩, 현재 적용된 조건 표시 (입력값과 확정 조건이 어긋나는 상태를 표시하는 것 포함)
- 검색 결과 구간 안내 외의 상세 통계
- 모바일/반응형 전용 레이아웃 최적화, 다크 모드 등 테마별 별도 스타일
- 다국어 지원 (UI 문구는 한국어로 통일)

### 데이터/서버

- 서버 측 검색(`json-server`의 `q`, `_like` 쿼리 등)과 페이지네이션
- 현재 적용 중인 검색 조건의 영속화 (새로고침 후 유지, URL 쿼리 파라미터 연동). 최근 검색어 목록의 `localStorage` 저장은 범위 안이다 (ADR-002)
- 최근 검색어의 기기/브라우저 간 동기화와 서버 저장, 다중 탭 실시간 동기화
- `NotesContext`에 검색 상태를 두는 것 (검색 상태는 `App`과 `SearchBar`가 소유)
- `db.json` 기존 노트 데이터 마이그레이션 (`tags`가 없는 노트는 `?? []`로 처리)

### 기타

- 접근성 고도화 (`aria-label` 이외의 스크린리더 안내 개선, 결과 건수 라이브 리전 등)
- 검색 성능 최적화(인덱싱, 대량 노트 가상화 목록)

## 5. 용어 정의

| 용어                | 정의                                                                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 검색 (Search)       | 검색 대상과 검색어를 지정해 노트 목록을 걸러내는 동작.                                                                        |
| `SearchBar`         | 사이드바 상단의 검색 컴포넌트(`src/components/SearchBar.tsx`). 선택박스, 입력창, 검색 버튼, 건수 문구로 구성한다.             |
| `SearchBarProps`    | `SearchBar` 컴포넌트의 props 인터페이스. `onSearch`로 확정 조건을 올린다.                                                     |
| 검색 대상 (`field`) | 어느 필드에서 찾을지 고르는 값. 전체 / 제목 / 내용 / 태그 중 하나이며 기본값은 "전체".                                        |
| 검색어 (`keyword`)  | 사용자가 입력창에 쓴 문자열.                                                                                                  |
| 확정 조건           | Enter 또는 검색 버튼을 눌러 `onSearch({ field, keyword })`로 올린 조건. `App`이 `useState`로 보관하고 필터링에 사용한다.      |
| 입력 중인 값        | `SearchBar`가 로컬 `useState`로 가진 선택박스 값과 입력 텍스트. 확정 전까지 목록에 영향을 주지 않는다.                        |
| 필터링 함수         | 필드와 검색어를 받아 노트를 걸러내는 순수 함수. trim, 대소문자 무시, `tags ?? []`를 처리한다.                                 |
| 부분 일치           | 검색어가 대상 문자열에 포함(`includes`)되면 일치로 보는 방식.                                                                 |
| 전체 검색           | 제목 OR 내용 OR 태그 중 하나라도 일치하면 결과에 포함하는 검색.                                                               |
| 필터 해제           | 확정 조건의 검색어가 trim 후 빈 문자열이 되어 전체 목록을 보여주는 상태. 선택박스 값은 유지한다.                              |
| 건수 문구           | 검색창 하단 좌측의 "검색 결과 N건". 확정된 검색어가 있을 때만 표시하며, 0건이어도 표시한다.                                   |
| 파생 계산           | 별도 저장 없이 `notes`와 확정 조건에서 매번 목록과 건수를 계산하는 방식.                                                      |
| 노트 없음           | `notes`가 비어 있는 상태. "노트가 없습니다"를 표시한다.                                                                       |
| 검색 결과 없음      | `notes`는 있으나 확정 조건에 맞는 노트가 0건인 상태. "검색 결과가 없습니다"를 표시한다.                                       |
| `SearchCondition`   | 확정 조건의 타입(`field`, `keyword`). `src/types/search.ts`에 둔다.                                                           |
| 조립 컴포넌트       | `useNotes()`를 호출해 데이터를 가져오고 순수 표현 컴포넌트에 props로 내려주는 최상위 컴포넌트.                                |
| `NoteSidebar`       | 사이드바의 조립 컴포넌트(`src/components/NoteSidebar.tsx`). 필터 결과와 건수를 계산해 `SearchBar`와 `NoteList`에 전달한다.    |
| 최근 검색어         | 확정된 검색(Enter/검색 버튼)을 최신 순으로 최대 10개까지 `localStorage`에 기록한 목록. `field + keyword` 중복은 제외한다.     |
| `RecentSearch`      | 최근 검색어 한 건의 타입(`field`, `keyword`, `searchedAt`).                                                                   |
| `useRecentSearches` | 최근 검색어 상태와 `localStorage` 읽기/쓰기를 캡슐화한 훅(`{ items, add, remove, clear }`). 규칙은 `utils/recentSearches.ts`. |
| 옵셔널 필드         | `tags?`처럼 없을 수도 있는 필드. 태그가 없는 기존 노트는 `note.tags ?? []`로 처리한다.                                        |
| trim                | 입력값 앞뒤 공백 제거.                                                                                                        |
| ADR                 | Architecture Decision Record. Context / Decision / Alternatives / Consequences로 기술 결정을 기록하는 형식.                   |
| PRD                 | Product Requirements Document. 기능의 배경, 사용자, 요구사항, 범위를 정리한 문서.                                             |
